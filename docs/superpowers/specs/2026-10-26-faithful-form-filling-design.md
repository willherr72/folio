# Faithful form answer publication

## Purpose and evidence

Ordinary form filling currently publishes PDFium's whole saved document. The new value is verified, but PDFium regenerates the appearance and can erase custom drawing around the answer. This is reproduced in text, dropdown and list fields through native filling and the Windows Apply/save workflow. The independent saved-PDF audit confirms the requested values and missing artwork.

Evidence and retained failed attempts: `artifacts/form-frame-design-20261026/investigation.md`. The native source-frame control reproduces the loss without any frame-edit experiment. `identity-probe/results.json` verifies operation-specific markers across three ordinary fields and a shared text field. `answer-publication-probe/results.json` verifies an original-graph answer transplant in those four cases, including both linked appearances, native reopen, and removal of temporary markers. These are trusted-fixture experiments, not production admission or implementation.

This is a prerequisite for border/background controls. The user authorized autonomous implementation and verification without routine approval checkpoints. Work proceeds inline; no commits, pushes, releases or changes to original user documents. Product/runtime stay frozen until the active binding regression ends.

## User-visible contract

Changing an answer updates the selected logical field and all its linked widgets. Unrelated field values, default answers, options, labels, actions, page content, comments, links, bookmarks and field hierarchy remain intact. Static drawing around the answer, including custom artwork and captions, survives repeated edits and save/reopen. Undo/Redo and recovery retain the complete original and resulting sources.

Continue supporting ordinary text, multiline text, editable dropdowns, index-selected dropdowns/lists, multi-select lists, checkboxes and radio groups. Keep current fill permissions, read-only/hidden/password/rich-text restrictions, stale expected-value checks, line-ending normalization, length limits and radio deselection rules. Do not route ordinary filling through the choice-settings editor's narrower text/model limits.

Answer layout remains generated by the native field engine, including field default font settings, wrapping, selection paint and font fallback behavior. This correction preserves surrounding artwork; it does not promise an arbitrary producer's old answer typography matches native regeneration. An unchanged normalized answer returns the original bytes after request validation. The UI keeps its existing Apply behavior and error presentation.

When the answer cannot be isolated without changing other paint, fail the private transaction with an actionable reason and retain the user's draft. Never retry a rejected preservation attempt by publishing the destructive native result. This is a compatibility limitation to measure and improve, not the project's completion criterion.

## Architecture decision

Publish from the original parsed PDF graph. Use native filling as the value and answer-layout oracle, never as the owner of unrelated source objects. This preserves original action targets and reference relationships and avoids importing the native serializer's unrelated changes.

The alternatives considered were repairing a wholly native-saved graph and changing PDFium's appearance generator. Repair would require proving correspondence for all unrelated source graphs after serialization. A renderer patch would expand a local fill-publication correction into the dependency and affect all appearance-generation consumers. Both introduce unnecessary ownership risk for this defect.

Keep `NativeForm::fill` available as a private raw generator for existing isolated probes. Add a preserving publisher at the worker's ordinary-fill boundary. It returns bytes into the existing registration, original-path, protection, imported-annotation and image-lease flow. No frontend API or new global runtime is needed.

### 1. Validate and bind the private probe

Extract existing request validation into `NativeForm::validate_fill` and reuse it from the raw fill and the preserving publisher. Validation must precede the no-op shortcut. Preserve exactly the current accepted value semantics.

Load the original through the bounded filling graph validation. Resolve the selected annotation to its terminal logical field using graph ownership, not a display name. Enumerate its linked widgets and all page/annotation placements, including repeated appearances. Record the parent/child and placement correspondence needed to validate the native result.

Use a fresh transaction-specific dictionary key, absent from the relevant source nodes, to mark the selected field owner, its ancestors needed for correspondence, and its widgets with bounded unique tokens. Marks exist only in a private probe. Verify each expected mark survives exactly once on the right node role and ownership relationships; reject missing, repeated, forged, detached or mismatched marks. Native object numbers and field names are not identity proofs. No mark is copied into the publication graph.

The original document remains the publication graph. Serialize a marked probe within the existing output limit. Existing action masking remains active during every native open/fill operation; no document scripts or external actions execute.

### 2. Capture native value changes

Run the validated request on the marked private document. Read the resulting scalar/array value entries through bounded dereferencing. Only the selected logical field's current-answer entries may change: `/V`, `/I`, and `/TI` where native semantics require them, plus linked button `/AS` entries. Preserve `/DV`, `/Opt`, field flags, `/DA`, resources and every unrelated metadata entry. Assert that the selected native values match the normalized request and that unrelated field state has not changed.

Preserve native export/display distinction and duplicate-label/index semantics. Do not invent choice values by joining labels or overwrite an inherited default merely because the current value is absent. Stage values on their correct original owners. Reject an unexpected change to another logical field rather than extending the edit's scope.

### 3. Replace answer paint only

For text and choice fields with saved appearances, parse and bound both source and generated appearance streams before cloning. Prefer an explicit `/Tx` marked answer region whose graphics/text/path effects are contained. Preserve original operations before and after that region, their order, appearance dictionary, bounds, matrix and non-answer resources.

Support ordinary unmarked appearances as well: a single unambiguous text object can identify a text-field answer. Preserve the graphics-state effects needed by following artwork. Reject text clipping modes or ambiguous multiple unmarked text objects rather than deleting possible captions. For an unmarked choice appearance, any non-text selection paint must also be identified; a simple border/background plus a single text object is supported, while unexplained selection-like paint cannot be assumed static. Existing unmarked fixtures in `form_filling.rs` are mandatory compatibility tests, not fixtures to weaken.

Generated list selection backgrounds belong to the answer region and must update with the selected rows. Empty answers retain an insertion location so later filling preserves the original layer order. Separate generated resources from source resources, or bind them through proven equivalence and collision-free names; matching a resource name is not enough. Use the existing bounded appearance copier and geometry helpers where applicable, without importing page/field/action ownership through resources.

Preserve the source appearance mapping and clipping contract. Mapping generated answer coordinates into it must be finite, invertible and tested for rotated, scaled and nonzero-origin appearances. Native answer drawing must not accidentally inherit source character spacing, text rise, render mode, transparency or transforms. A bounded, explicitly initialized private answer form is an available implementation technique; a nested form must not enlarge the old answer clip or change foreground/background order.

Checkbox/radio values normally switch an existing appearance state. Keep every original normal/down/rollover state and its artwork, updating only the valid selected state and logical value. If a needed normal appearance is absent, use a bounded native-generated normal appearance while preserving other existing modes. Do not replace a custom state dictionary just to toggle it.

### 4. Missing appearances and global regeneration

Missing appearance data is different from ambiguous custom drawing. Capture the initial native effective appearance before applying the value change when it is needed to establish a baseline; it can supply missing appearances without inventing an answer region.

`/NeedAppearances true` explicitly requests global regeneration. The first investigation's no-edit control already regenerated its custom paint, so raw saved appearances are not a reliable baseline in that case. Preserve the initial native effective display, then apply the answer change. If normalizing this flag to false is necessary for stable reopen, first materialize and validate the effective appearances for every affected widget, including unrelated fields. Do not clear the flag while leaving unrelated fields without their required appearance. Keep the original field values and graph. Treat an unprovable global regeneration transaction as an explicit failure, not a silent partial normalization.

Normal `/NeedAppearances false` or absent documents retain unrelated appearances directly. The source and initial native view must be reconciled before assuming that initialization caused no changes. No-op publication still returns the exact source bytes.

### 5. Atomic publication and bounds

Stage all linked value and appearance changes before modifying the private publication graph. Validate the saved result by reopening it natively, checking the complete selected value and relevant linked states, and comparing unrelated field state. Registration occurs only after these checks. Original bytes, history, paths and recovery ownership remain unchanged on failure.

Retain the existing 512 MiB document/output limit, 4000 form-node/placement validation, 100000 graph-value traversal bounds and 64-level graph depth. Keep the current 32768 UTF-16-unit text limit. Appearance decoding is limited to 4 MiB and 262144 operations per stream, with a 64 MiB aggregate retained appearance/resource budget. Charge before decompression, allocation, clone, repeated-reference expansion or graph import. Share import memoization across linked appearances and avoid copying an embedded font once per widget. Preserve existing lower limits in other appearance editors; this fill path must not silently broaden them.

Parsing/rendering working sets are separate from retained graph budgets. Exercise compressed-stream expansion, oversized operands, linked alias amplification and repeated fills. Prune obsolete generated appearance resources after successful staging while preserving reachable source objects and aliases. Temporary markers and intermediate probe documents never enter recovery or user output.

## Verification and completion

Native regressions must reproduce the three observed losses first, then verify retained artwork, current values and defaults after repeated fill/clear/refill, shared widgets, save/reopen and recovery. Check both marked and unmarked text, lists with actual selection paint, field-local font aliases, matrices/rotation/UserUnit, missing appearances, global regeneration, buttons, stale requests, malformed graphs and aggregate budgets.

Run the existing form-filling, choice publication, form appearance/position, protected-source and source-ownership regressions. Run the frontend regression/build gates appropriate to any integration changes. Run the corrected Windows Apply, Undo/Redo and save/reopen workflow on fresh copies; independently inspect and rasterize saved PDFs. One scoped final review follows implementation, with corrections applied inline. Do not call the milestone complete from the throwaway probe or a passing value-only check.

Border/background controls remain the next visible feature after this prerequisite is verified. Adobe/Foxit parity remains unproven.
