# Issue 14 acceptance status

v0.10.1 completes two additional pieces of the shaped text-box implementation:
whole-grapheme deletion and support beyond 255 distinct semantic definitions.
Issue #14 remains open. The restrictions below are deliberate reader-compatibility
gates, not claims of support or completed manual acceptance.

| Acceptance area | Verified | Still pending |
| --- | --- | --- |
| Native shaping | Ligatures, composed/decomposed accents, combining marks, Arabic joining, Indic and supplementary Unicode fixtures; missing-glyph and resource refusals | Mixed direction and RTL word separators/joiners |
| Portable text | Exact logical Unicode in PDFium, MuPDF and pypdf; editable font/settings restoration; wide-font native save/reopen | Foxit/Acrobat interactive copy/search acceptance |
| Geometry | Original visible outlines retained; 24 wide native cases at four rotations, original/resaved; shared cluster boxes and pinned reader-padding model | Equivalent cluster selection in other readers is not claimed |
| Editing | Grapheme-safe plain Backspace/Delete; ligature interiors remain separate letters; RTL-mark boundaries; native undo/redo; WebView composition | Physical Windows IME acceptance; direct canvas caret editing remains excluded |
| Lifecycle | Existing cancellation/stale request/font ownership/search/recovery regressions; wide editable and flattened roundtrip without source font | No new lifetime gap identified |
| Bounds | Existing 4,096 scalars/16,384 UTF-8 bytes and hostile-font guards; deterministic synthetic font capped at 4,096 definitions and 256 KiB | Larger source-text budgets are outside this change |

## Wide semantic font

Existing boxes with at most 255 definitions retain their byte-compatible Type3
representation. Larger boxes use one Type0/CIDFontType2 resource and one TJ array,
with synthetic rectangle metrics enlarged 16 times and inverse text size. These
rectangles use invisible text rendering; exact original-font outlines still
provide all visible ink. The synthetic font is generated by Folio, not derived
by modifying an imported font. Out-of-range metrics fail explicitly.

The [native verification](issue14-native-wide-verification.json) covers 48 PDFs:
24 original/native-export pairs. All three readers return exact Unicode. The
original font, semantic font, visible content and raster output survive export.
PDFium deliberately pads TrueType character tops by integer top/64; the pinned
source model explains all observed edges to 0.00000763pt. Shared-cluster edges
differ by at most 0.002198pt, below Folio's existing 0.02pt grouping threshold.
The [investigation](issue14-wide-semantic-probe.md) retains the failed baseline
comparisons and the evidence explaining the padding. No glyph is distorted to
cancel a reader-specific adjustment.

The native font's hhea/OS/2 metrics retain an ascent/descent envelope expanded to
include its glyph bounds; the PDF descriptor uses tight bounds. MuPDF has its own
selection-box behavior, which is not asserted equivalent to Folio/PDFium.

## Editing and outstanding bidi gate

Content selects complete graphemes before asking the browser to delete. This
preserves native edit/undo transactions and exact Unicode. Modified shortcuts,
composition and legacy text keep their existing behavior. Eleven real Chromium
cases include trusted non-keyboard backward/forward deletion commands, caret
positions, one committed edit and undo/redo. Physical IME acceptance is separate.

A further 64-copy policy matrix tested original metadata, viewer right-to-left
preferences, ReversedChars marked content, and language/direction hints over
existing native mixed/Arabic fixtures. None repaired mixed-direction Unicode
across all readers. For example, `ABC سلام 123 DEF` becomes `ABC مالس 123 DEF`
in raw PDFium with logical TJ ordering; visual ordering instead gives
`ABC 123 سلام DEF`. pypdf also drops runs in these cases. The source text is never
silently reordered to disguise those failures. `scripts/probe-bidi-reader-policy.py`
retains this bounded metadata experiment; it is not a fully tagged-PDF implementation.
A working bidi representation still needs exact text and character geometry before
those inputs can be enabled or issue #14 can be closed.
